## Supabase setup

```bash
# 1. Install dependencies (already done)
npm install

# 2. Copy environment variables and fill in your project values
cp .env.example .env.local

# 3. Link the CLI to your hosted project (once)
npx supabase login
npx supabase link --project-ref <your-project-ref>

# 4. Push migrations to the hosted database
npm run db:push

# 5. Generate TypeScript types from the linked schema
npm run db:types
```

Local development (requires Docker):

```bash
npm run db:start     # boots the local Supabase stack
npm run db:reset     # re-applies every migration
npm run db:stop
```

> `supabase/config.toml` was generated by `supabase init`. Extensions live in
> the `extensions` schema, as on hosted Supabase.

## Supabase-specific decisions

1. **Auth lives in `auth.users`.** `public.users` is a profile/membership table
   keyed by `auth.users.id`; `password_hash` was removed. An `auth.users` insert
   trigger creates the profile and reads an optional `org_id` from admin-only
   `app_metadata` (never user-editable metadata, so users cannot join a tenant
   by passing an `org_id` at signup).
2. **Onboarding is a database function.** `public.bootstrap_organization(name,
   code, timezone, currency)` creates the tenant, an Administrator role with all
   permissions, links the caller, and seeds master data, pipeline stages, leave
   types, expense categories, UoMs, a main warehouse, a price list, a shift and a
   default territory.
3. **RLS is enforced twice.** Every row is restricted to `current_org_id()` and
   module/action access is checked with `has_permission(module, action)`.
   `role_permissions.data_scope` is stored but row-level data scoping
   (own/team/territory/org) is still enforced in the query layer.
4. **PostGIS is schema-qualified.** Extensions are created in `extensions`, and
   geo columns use `extensions.geography(...)` so migrations do not depend on a
   session `search_path`.
5. **`location_pings` is partitioned monthly.** Partitions are created for the
   current + next three months. Call
   `select public.ensure_location_ping_partitions(3);` from `pg_cron`.
6. **Stock is ledger-first.** Inserting a `stock_movements` row atomically
   upserts `stock_levels` through a trigger. `stock_levels` uses a surrogate id
   and an expression unique index because `batch_id` is nullable. Because the
   trigger is `SECURITY DEFINER`, it verifies that the warehouse, product and
   batch all belong to the movement's `org_id` before writing.
7. **Storage paths are tenant-prefixed.** Object paths must start with
   `<org_id>/`; policies compare the first folder to `current_org_id()`.
8. **Reporting views are `security_invoker`.** The Reports Builder should expose
   only these curated views, never raw tables.
9. **System reports are global.** `report_definitions.org_id is null` marks a
   prebuilt report; schedules and runs carry their own `org_id` so they stay
   tenant-scoped.
10. **Permissions are exposed through one RPC.** `current_permissions()` returns
    only `auth.uid()`'s effective module/action/data-scope rows, because RLS
    hides the role tables from users without `administration.view`. The role-aware
    sidebar and dashboard use this single call instead of dozens of checks.
11. **Audit writes are centralized.** `log_audit()` is `SECURITY DEFINER`, skips
    writes when the caller has no tenant yet (during onboarding), and is called
    by both the generic CRUD layer and table triggers.
12. **Relationship checks are app-layer plus database helpers.** The generic
    CRUD layer validates every relation with `parent_belongs_to_org()`, so a
    record cannot point at another tenant's parent row.
13. **Offline submissions carry a client UUID.** Seven high-volume tables have
    `client_uuid` and `synced_at`; field actions send `crypto.randomUUID()` and
    a unique index prevents duplicate retries.
